# 派工 prompt 模板

給主對話（orchestrator／維護 session）派遣 subagent 時直接套用。`<>` 是填空。
模型與 effort 的選法**一律查 `model-dispatch.md` 的對照表**，本文不重複。

## 通用規則（每個模板都適用）

1. **三件套缺一不可**：目標與動機、驗收條件、回報格式。動機讓 subagent 能自行
   補足你沒想到的細節；驗收讓它知道何時停；回報格式保護主對話的 context。
2. 路徑一律**絕對路徑**（subagent 的工作目錄可能不是專案根；git 指令提醒加
   `-C <專案根>`）。
3. 一次派一件事。兩個目標就派兩個 subagent，不要合併。
4. 回報合約預設：**結論先行、位置用 檔案:行號、長產物寫入系統暫存目錄回傳路徑、
   絕不寫入目標專案**。
5. 驗收永遠交給**沒參與產出**的 context（見 judgment-rubrics.md R5）。

## T1 搜尋（找檔案／符號／設定／事實）

```
【目標】找出 <要找什麼>。動機：<拿到結果之後要做什麼決定>。
【範圍】從 <絕對路徑> 開始；已知線索：<關鍵詞／可能的檔名／命名慣例>。
【驗收】每個結果附 檔案:行號 + 一行說明；一無所獲時列出已搜過的位置、
       用過的關鍵詞與排除依據——「沒找到」也要有證據。
【回報】不超過 20 行：一句結論 + 結果清單。不要貼檔案內容全文。
```

## T2 實作（新增功能／修 bug）

```
【目標】<做什麼>。動機：<對應哪個 story／需求，為什麼需要>。
【邊界】只允許修改：<檔案／目錄清單>。禁區：<明確不可動的檔案，含理由>。
【作法約束】<必須遵循的規範檔路徑，如憲章、tech-standards>；遇到需要取捨的
       設計決定（兩個都能動的方案）先停下回報選項，不要自行拍板。
【驗收】<測試指令> 全綠；每個新行為有對應測試；`git status` 中不出現邊界外檔案。
【回報】不超過 30 行：修改檔案清單（檔案:行號範圍）、執行過的驗證指令與結果、
       未解決事項。不要貼整段程式碼，diff 留在 working tree 裡。
```

## T3 重構（行為不變的結構調整）

```
【目標】重構 <對象>。動機：<為什麼值得動它>。**外部行為不得改變。**
【基準】動手前先跑 <測試指令>，記下通過數作為基準；沒有測試就先停下回報，
       不要在無基準的情況下重構。
【邊界】只允許修改：<清單>。變更 public 簽名時，列出**全部**呼叫端並同步修改。
【驗收】重構後同一測試指令結果與基準一致；無新增 TODO／註解掉的殘碼。
【回報】不超過 30 行：動了什麼結構、呼叫端同步清單、基準前後對照。
```

## T4 研究（查文件／查網頁／查生態系）

```
【目標】回答：<具體問題>。動機：<這個答案會決定什麼>。
【要求】答案分三級標注：「文件明確寫」／「多來源一致」／「推測」，各附來源 URL
       或檔案位置；查不到就寫查不到，禁止用訓練記憶充當查證結果。
【驗收】每個結論都有級別與來源；與問題無關的背景不要寫。
【回報】不超過 30 行：結論先行，來源清單收尾。
```

## T5 審查（code review／文件審查）

```
【目標】審查 <diff 範圍或檔案清單>。基準：<憲章／規範／spec 的檔案路徑>。
【要求】只報「說得出位置與後果」的問題：每項附 檔案:行號、嚴重度
       （MUST-FIX＝違反基準或會出錯；SHOULD-FIX＝品質建議）、具體修法。
       無發現時列出已檢查的面向，證明不是沒看。
【驗收】每個 MUST-FIX 都可獨立驗證（別人照你的位置與描述能重現判斷）。
【回報】結論行 + 發現表，不超過 80 行；溢出寫暫存檔回傳路徑。
```

## T6 升級交接（judgment-rubrics.md R1 觸發時，把任務交給更強模型）

```
【原任務】<把原本的目標／邊界／驗收整段照抄，不要摘要>
【失敗軌跡】第 1 輪：做了 <X> → 結果 <錯誤 A（原文訊息）>。
           第 2 輪：做了 <Y> → 結果 <錯誤 B（原文訊息）>。
【已排除】<確定不是的原因，附依據>
【目前懷疑】<現在的假設——標明這只是假設>
【要求】從頭獨立判斷，不必沿用上面的假設；若判定原任務的驗收條件本身有問題，
       先回報，不要直接改驗收。
```

## 反模式（看到就改）

- 「幫我看一下這個」——沒有目標、沒有驗收，subagent 只能猜。
- 把兩個任務塞一個 prompt——回報會混在一起，失敗時無法定位。
- 讓實作者自己宣告驗收通過——違反 R5，驗收必須另派 context。
- 派工 prompt 用相對路徑——subagent 工作目錄不同，直接跑錯地方（E2E 實證）。
- 要求「回報越詳細越好」——主對話 context 是稀缺資源，要結論不要過程。
