# 判斷準則（judgment rubrics）

給執行 SDD 流程的 orchestrator 與維護本 repo 的模型。每條準則＝**可檢查的訊號**＋
正例＋反例，不依賴直覺。遇到「該不該升級／算不算完成／要不要問人／是不是方向錯了」
的猶豫時，查對應小節照做；訊號不成立就不要行動。

配套文件：模型選擇與升降級的操作步驟在 `model-dispatch.md`；派工用的 prompt 模板在
`delegation-templates.md`。

## R1 何時升級模型（或加第二意見）

**任一訊號成立即升級，不要「再試一次看看」：**

1. 同一子任務**第二次失敗，且兩次失敗原因不同**（修好 A 冒出 B）——這是理解錯誤，
   不是手滑；重試只會出第三種錯。
2. 指定了 haiku 的任務**錯一次**就直接升級——它的重試不會更好，反而燒掉一輪往返
   （sonnet 才是預設，haiku 是有省成本理由才指定的，見 model-dispatch.md §2）。
3. 任務本質是**取捨而非執行**：兩個都能動的方案選一個、API 介面設計、命名體系、
   錯誤處理策略。執行型模型會給你「一個能動的」，不是「該選的」。
4. 你發現自己在**猜驗收標準**——連驗收都寫不出來的任務，先回 R3（問使用者）或
   升級模型把驗收定義出來，不要帶著模糊往下做。

- 正例：派 Haiku 批次改 import 路徑，它漏掉動態 import 改錯一批。→ 依訊號 2，
  直接升 Sonnet 重做**整批**（不是只補漏的那幾個），並把 Haiku 的錯誤模式寫進派工 prompt。
- 反例：跑測試第一次紅、重跑就綠（flaky test）。→ 這是環境訊號不是能力訊號，
  不升級；記錄 flaky 測試名稱，繼續原任務。

升級時必附完整失敗軌跡（做了什麼、期待什麼、實際得到什麼、已排除什麼），
格式見 `delegation-templates.md` 的「升級交接」模板。

## R2 何時算真的完成

**定義：完成＝每條驗收條件都有證據，證據＝執行結果，不是「程式碼看起來對」。**

收工前逐項核對：

- [ ] 驗收條件逐條列出，每條附 PASS 證據（實際執行的指令＋關鍵輸出）。
- [ ] 測試套件綠燈，貼出指令與 summary 行（不是「測試應該會過」）。
- [ ] `git status --porcelain` 為空，或每個殘留檔案都能說出歸屬。
- [ ] 回報文字裡沒有「應該」「理論上」「大概」——出現任何一個，就是還沒完成，
  回去補證據。

- 正例：validator 對 US1 的三條驗收情境各附執行指令與輸出，全 PASS。→ 完成。
- 反例：「程式碼已完成，邏輯上涵蓋所有驗收情境，測試檔也寫好了。」→ 沒有執行
  紀錄＝未完成。跑完測試、貼出結果才算數。

## R3 何時停下來問使用者

問的成本是一次往返；不問而做錯的成本是全部重做。**必問**（任一成立）：

1. 動作**不可逆**且超出原始指示：刪檔、push、改共用設定、對外發布、覆寫非自己
   建立的檔案。
2. 兩個合理解讀會導向**不同交付物**（規格歧義），且文件（spec/plan/憲章）判不了。
3. 發現**與使用者陳述矛盾的事實**（使用者說檔案在 X，實際不在）——先回報矛盾，
   不要替使用者「修正」他的說法。
4. 修正迴圈到上限（SDD 流程為 3 輪）。

**不問、自己解決**（全部成立）：可逆＋符合原始意圖＋文件已有答案或屬實作細節。

- 正例：spec 說「登入失敗顯示錯誤訊息」，沒說連續失敗是否鎖定帳號。兩種做法
  交付物不同。→ 問，附兩個選項與各自影響。
- 反例：測試框架選 pytest 還是 unittest？plan.md 已寫 pytest。→ 不問，照 plan 做。
  問這種問題等於把已決策的事丟回給使用者。

問的格式：AskUserQuestion，每題附選項與影響說明；一次把同批問題問完，不要擠牙膏。

## R4 方向錯了的訊號（換路，不要重試）

**任一訊號成立，停止當前做法：**

1. 連續兩輪修正，每輪冒出**新位置的新錯誤**——底層假設錯了。停下，重讀 spec 與
   plan，把「我以為」的假設逐條寫出來核對，從假設改起。
2. 你想「放寬檢查」「跳過這條測試」「先註解掉」來讓閘門通過——這是方向錯誤的
   **確定訊號**。絕不放寬，回頭找根因；找不到根因就走 R1 升級。
3. diff 持續變大，但驗收通過數沒有增加。
4. 需要動的檔案超出影響邊界報告——先判定「邊界錯」還是「實作錯」，
   對得回該 story 任務的就更新邊界認知並記錄，對不回的就是實作走偏。

- 正例：修 A 導致測試 B 壞，修 B 導致 C 壞。→ 停（訊號 1），重讀 spec 發現對資料
  格式的假設錯了，改假設後一輪修完。
- 反例：同一個錯誤訊息、同一個位置，原因是打錯變數名。→ 手滑不是方向錯，
  直接改對重跑即可。

## R5 品質底線怎麼驗（驗證不自驗）

**原則：產出者不能當自己產出的驗收者。**同一個 context 既做實作又判合格，
等於沒驗。

| 產出類型 | 驗法 |
|---------|------|
| 文件／規則檔 | 派 fresh-context agent 讀檔後回答「這份文件要你做什麼、判準是什麼」；答偏了＝文件寫得不清楚，改文件，不是怪讀者 |
| 程式碼 | 測試或實跑，由另一個 context（validator）執行並判定，證據標準見 R2 |
| 高風險判斷（架構、安全、不可逆操作）| 第二意見：另派一個 agent **不給它第一個結論**獨立判斷；兩者矛盾 → 升級模型或問使用者 |
| 難題（一次做對機率低）| 多答案評審：同題派 2–3 個獨立 agent 產出方案，再派一個只做裁判的 agent 選優並說明取捨 |

- 正例：寫完 model-dispatch.md 後，派一個沒參與撰寫的 agent 讀它，問「Haiku 錯一次
  該怎麼辦」，它答對＝文件可用。
- 反例：「我重讀了一遍自己寫的檔案，確認沒問題。」→ 作者重讀只能抓錯字，
  抓不到「別人讀不懂」，不算驗證。

## R6 模糊題與品味題（harness 的極限，誠實條款)

拆解、閘門、fresh-context 驗證能補**執行品質**；以下兩類補不了，遇到照表處置：

| 類型 | 識別訊號 | 處置（依序嘗試）|
|------|---------|----------------|
| 模糊題 | 驗收條件寫不出來；同一句需求兩人會做出不同東西 | ① 卡在 clarify 問使用者（附選項與影響）② 使用者不在場 → 停在該階段，把問題寫進狀態報告等裁決。**不要猜完直接做** |
| 品味題 | 多個方案都「對」，差在優雅度／一致性／長期維護性 | ① 升級模型做一次性評審 ② 多答案評審選優（R5）③ 都不可行 → 明說「此為品味判斷，本 harness 無法保證品質」，列出取捨交使用者 |

**禁止**：用「反正能動」掩蓋品味問題不報告；用自己猜的解讀填補模糊需求不標注。
兩者都是把風險藏到未來。
