# 決策模式提問框架

一次只問一組，用 AskUserQuestion；選項文字直接取自基線表格，提問前先 grep 那張表。
使用者答不出的先標「待確認」，摘要中保留。團隊已宣告過導入階段的，第 4 組只核對。

基線檔案一律指 `$SKILL_DIR/references/baseline/` 下的副本。

## 第 1 組：專案類型（成熟度／意圖）

- **查表**：`constitution.md`「團隊專案類型 × 風險分級對照」
  （`grep -n "團隊專案類型" constitution.md`，讀到下一個 `###` 之前）。
- **問法**：這個專案屬於表中哪一種？選項＝表的第一欄；每個選項的 description 帶上
  第二欄的預設風險分級。
- **為什麼問**：專案類型給出「預設風險分級」的起點。
- **判定**：預設分級＝表的第二欄。Spike／Tweak → 追問母服務是哪個、其分級為何，
  直接套用母服務分級。

## 第 2 組：風險因子（出錯的後果）

- **查表**：同上表第三欄「升級／調整條件」＋「服務風險分級」表的「典型情境」欄
  （`grep -n "服務風險分級（Service Risk Tiers）" constitution.md`）。
- **問法**（multiSelect）：把調整條件拆成可勾選的因子，例如：金流、認證授權、核心交易、
  個資／PII、對外 SLA、對外開放、將轉正式且處理真實資料、純內部唯讀輔助。
  條目以當前版本的表為準。
- **判定**：依表的調整條件取最高分級；憲章規則「無法判定且可能涉及敏感資料 → Critical」、
  「未標示 → Standard」。憲章的解說例子要記得：POC 直接讀寫正式個資庫 → Critical；
  正式專案但只是內部唯讀儀表板 → 可降 Internal。
- **產出**：風險分級＋一句理由，理由指向勾選的因子。

## 第 3 組：應用類型（決定載入哪些憲章文件）

- **查表**：`constitution.md`「我的專案是…｜須載入文件」表
  （`grep -n "我的專案是" constitution.md`，連同表下方兩段引文一起讀）。
- **問法**：選項＝表的第一欄（「任何應用（共通基線）」那列不是選項）。選「工具服務」時
  追問：以 shell 實作？對外提供 API？需容器化部署？
- **判定**：載入文件＝表的第二欄。`app_type` 對應值（sdd-harness adoption schema）：
  API 服務 → `api-service`、微服務 → `microservice`、工具服務 → `tool-service`、
  Shell Script → `shell-script`、前端網頁應用 → `frontend-web`。
- 一個 repo 有多種可部署單元（如前後端同 repo）：每個單元各判一次，摘要分列。

## 第 4 組：團隊成熟度（決定導入階段）

- **查表**：`README.md`「三階段導入總覽」＋各階段章節的「進入第 N 階段的條件」
  （`grep -n "進入.*階段的條件\|進入「完整導入」的條件" README.md`）。
- **問法**（multiSelect，勾選已成立的）：把「進入第二階段的條件」與「進入第三階段的條件」
  逐條列為選項，提問前先呈現三階段總覽表，讓使用者看到每階段的必要／參考範圍。
- **判定**：
  - 進入第二階段的條件未全部成立 → 第 1 階段。
  - 全部成立、進入第三階段的條件未全部成立 → 第 2 階段。
  - 兩組都全部成立 → 第 3 階段。
  - 階段是團隊層級、循序晉級、不跳級；團隊已宣告階段時以宣告為準，本題只核對是否仍成立。
    專案本身的輕重由風險分級承擔（Experimental 在階段 2 的 TR 多為 MAY），不用降階段處理。
- 階段 1 時風險分級的標示為 SHOULD（仍記進摘要）；階段 ≥ 2 為 MUST。

## 第 5 組：覆述確認

把前四組結果連同「載入文件」「本階段 MUST／參考範圍」一次覆述
（例：「階段 1 ＋ Shell Script ＋ Internal → constitution.md（CP／GV 為必要）＋
constitution-shell.md（參考）」），請使用者確認或指出要改哪一項；改了就只重判受影響的項目，
確認後才產出摘要。
